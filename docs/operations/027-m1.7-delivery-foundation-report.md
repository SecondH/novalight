## 2. Implementation Status

### Repository workflow (Task 2)

- **`.github/PULL_REQUEST_TEMPLATE.md`** (new) — implements [Development Workflow §10](../development/015-development-workflow.md)'s five required PR sections (Summary/Reason/Impact/Testing/Risks) plus a quality-gate and account-isolation checklist.
- **Branch strategy** — [Development Workflow §8](../development/015-development-workflow.md) already documents `feature/`/`bugfix/`/`refactor/`/`docs/` prefixes; unchanged, no new work needed. Note (pre-existing, not fixed): the current working branch `chore/claude-workspace-bootstrap` uses a prefix not in that list — cosmetic, not touched (renaming an active branch is a git operation outside this session's scope).
- **Branch protection rules** — cannot be applied via API (no live repo, no `gh` CLI). Documented checklist for whoever creates the repository:
  - Require status checks to pass before merging: the `validate` job from `.github/workflows/ci.yml` (lint, typecheck, migrations, test, build).
  - Require at least one PR review before merge (reviewer identity/CODEOWNERS intentionally not specified — no documentation-ownership role is named yet, a pre-existing open risk; inventing reviewer usernames would be worse than leaving this blank).
  - Disallow direct pushes to `main`, matching [Development Workflow §8](../development/015-development-workflow.md) ("Main Branch: production-ready, protected, reviewed changes only") and the repository's own `protect-main-branch.js` hook, which already enforces this locally regardless of remote settings.
  - Disallow force-push to `main`.

### CI/CD architecture (Task 3)

```text
GitHub Actions (.github/workflows/ci.yml) -- "validate" job, triggered on push to main / PR:

checkout → setup-node → install
  ↓
lint (turbo run lint)
  ↓
typecheck (turbo run typecheck)
  ↓
[NEW] apply database migrations (prisma migrate deploy, against an ephemeral
       postgres:16-alpine service container -- port 5432, torn down every run,
       a deliberately placeholder-shaped password recognized by
       .claude/hooks/block-secrets.js, chosen after that hook correctly blocked
       a less-obviously-placeholder value on first attempt)
  ↓
test (turbo run test, RUN_DB_INTEGRATION_TESTS=1 -- the previously-local-only
      ownership-isolation tests now run in CI too)
  ↓
build (turbo run build)

[NOT ADDED] deploy -- still explicitly out of scope, per the standing "no production
            deployment yet" instruction carried from M1.6.
```

This is the full "CI validation pipeline" the task asked for — genuinely enhanced (Postgres service + migration step, both new and verified working), not merely documented. It stops exactly at validation; no deploy job exists.

**Verified, not assumed:** the exact `migrate:deploy` command used in the workflow was run locally against a real database and confirmed to work; the workflow YAML was parsed with `js-yaml` and confirmed structurally valid (8 steps, `postgres` service present) before being considered done.

**CORS hardening (closes a gap flagged in M1.5/M1.6):** `apps/api/src/middlewares/security.ts`'s CORS check was previously a binary `NODE_ENV === 'production'` test that didn't distinguish staging from development. Now supports an explicit `CORS_ALLOWED_ORIGINS` env var (comma-separated allow-list); falls back to the exact prior behavior when unset — verified byte-for-byte unchanged by independent architecture review, not just claimed. 4 new tests, including a fail-safe edge case (a malformed allow-list value blocks all origins rather than silently permitting them, even in production).

### Vendor activation plan — Clerk / Supabase / Vercel / Railway (Task 5)

**Prepared, not executed** — each of these requires the user's direct action (account creation, billing if applicable, credential handoff). Concrete, ordered checklist:

1. **GitHub** — create the repository (or confirm one exists); provide the remote URL so `git remote add origin <url>` can be run and `.github/workflows/ci.yml` starts actually executing. Blocks everything below that depends on CI running for real.
2. **Clerk** — create a development instance at dashboard.clerk.com; copy the secret key into a local `.env` (never committed) as `CLERK_SECRET_KEY`; this alone is enough to validate `apps/api/src/auth/clerk-auth-provider.ts` end-to-end for the first time (currently only mocked-SDK-tested, per [ADR-020](../architecture/026-clerk-development-integration-decision.md)). Activating it as the live provider (swapping the import in `apps/api/src/middlewares/authentication.ts`) additionally requires a `security-reviewer` sign-off on the activation itself, per that ADR.
3. **Supabase** — create one project for staging (a second, separate project for production, per [023-environment-strategy.md](./023-environment-strategy.md) §6's isolation requirement — never share one project across environments). Run `prisma migrate deploy` against it once created.
4. **Railway** — create a service for the backend (`apps/api`), connected to the GitHub repo from step 1 for auto-deploy; set environment variables per [023-environment-strategy.md](./023-environment-strategy.md) §2 (`DATABASE_URL` from step 3, `CLERK_SECRET_KEY` from step 2, `CORS_ALLOWED_ORIGINS` set to the real Vercel deployment URL from step 5).
5. **Vercel** — create a project for the frontend (`apps/web`), connected to the same GitHub repo, with `NEXT_PUBLIC_API_URL` pointed at the Railway service from step 4.

Steps 2-5 can happen in parallel once step 1 is done; none of them are blocked on each other, only on having a repository to connect to.

### Secrets management verification (Task 6)

- `packages/database/.env` re-verified: `git check-ignore -v` confirms it's excluded; `git status --short` confirms it was never staged; the repository has zero commits on any ref, so it categorically cannot have been committed.
- `.gitignore`'s `.env` + `.env.*` (with `!.env.example` preserved) pattern, fixed in M1.6, re-confirmed unchanged and correct.
- `.claude/hooks/block-secrets.js`'s M1.6 fix (compound identifier detection) re-verified intact by independent security review — traced the CI workflow's own Postgres-password line through the actual regex, confirmed it still matches the compound-identifier pattern and correctly allows the recognized placeholder value.
- **New gap found this session (not introduced, pre-existing, now documented):** `block-secrets.js` matches secrets in `KEY` + assignment-operator + value shape but does not independently catch a credential embedded inside a connection-string/URL value (e.g. a database URL with a real password in it) — the CI workflow's own database-URL line reuses the same placeholder value as the password line above it, so this didn't cause an actual leak here, but the hook would not have caught it independently if it had been a different, real value. Recorded as a known hook limitation, not fixed this session (a URL-credential regex is a distinct, non-trivial addition — worth its own scoped pass, not bundled into this report).

## 6. M2 Readiness Assessment

**Still not ready — consistent with M1.6's assessment, for the same reasons plus one now-closed item.**

What changed since M1.6: the CI validation pipeline is now genuinely complete (would pass end-to-end the moment a real repository exists), CORS is environment-aware, and the CI/CD platform decision is formally closed. What has **not** changed: no live repository, no live vendor accounts, backup/recovery still undocumented, RBAC still open. M2 product-feature work should not begin until the repository-hosting blocker closes and at minimum the Clerk/Supabase staging path (§2, steps 1-3) is real — a team-ready development environment needs a place for the team to actually collaborate, which remains the one thing this session could not create on its own.
