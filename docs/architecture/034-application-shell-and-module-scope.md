## Context

[028-m1-technical-design.md](./social-ai-platform/028-m1-technical-design.md) §4.1 already documents a route plan (`(dashboard)/content/`, `(dashboard)/calendar/`) and §4.6 explicitly excludes settings/team/billing UI from M1. Repository discovery (2026-07-14) confirmed the **backend is real** for more than the frontend currently exposes:

| Endpoint                                                                              | File                             | Real?                                                                       |
| ------------------------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------- |
| `POST /accounts`, `GET /accounts/me`                                                  | `apps/api/src/modules/accounts/` | Yes — auth-required, Zod-validated                                          |
| `POST /brands/intake`, `GET /brands/me`                                               | `apps/api/src/modules/brands/`   | Yes — auth-required, rate-limited, Zod-validated                            |
| `POST /content/ideas/generate`, `GET /content/ideas`, `POST /content/ideas/:id/draft` | `apps/api/src/modules/content/`  | Yes                                                                         |
| `PATCH /content/drafts/:id`, `.../approve`, `.../discard`, `.../schedule`             | same                             | Yes                                                                         |
| `GET /content/calendar`, `.../reschedule`, `.../posted`, `.../discard`                | same                             | Yes                                                                         |
| `POST /ai/text/generate`                                                              | `apps/api/src/modules/ai/`       | Yes — generic Groq-backed text-gen primitive; not itself a user-facing page |

**Correction (2026-07-14, after independent architecture review traced the actual wiring):** the `/ai/text/generate` primitive above is **not** consumed by the Brand or Content services. Two entirely separate AI abstraction paths exist in `packages/ai-core`: the `AiProvider` interface (`GroqAiProvider`/`MockAiProvider`), wired only into `ai-text-generation.service.ts` behind `/ai/text/generate`; and the `ModelProvider` interface, implemented **only** by `FakeModelProvider` (`apps/api/src/ai/fake-model-provider.ts`), which is what `content.service.ts` and `brands.service.ts` actually construct their agent executors against. In plain terms: the brand-profile interpretation, content ideas, captions, and visual prompts a user sees on the Brand Setup and Content pages today are deterministic canned output from `FakeModelProvider`, not live Groq/LLM output — matching [028-m1-technical-design.md](./social-ai-platform/028-m1-technical-design.md) §5's explicit M1 scope ("no external AI provider is connected in M1... agent runtime... against a test/fake provider only"). This doesn't change this ADR's module-status verdicts (Content/Calendar's "Implement Now" status rests on the real, tested CRUD/workflow layer, independent of whether idea generation is AI-real or template-fake) but the original wording overstated what's live — flagged and corrected here per CLAUDE.md's "report, don't silently resolve" rule.

Per [ADR-030](./030-authentication-activation-strategy.md), Clerk auth is now **live for local development** (not just an in-memory stand-in). Database migration state: applied locally per ADR-030's verification steps.

**Frontend gap**: only a `brand-setup` skeleton page exists. There is **no page for account/vertical creation** even though `POST /accounts` is real and `BrandSetupForm.tsx`'s own comment states it "assumes an Account already exists" — this is a genuine missing step, not a documented future-scope item. There are **no Content or Calendar pages at all**, despite real, tested API support for both.

## Decision

### Application shell architecture

```text
app/[locale]/(dashboard)/
├── layout.tsx        # sidebar (desktop) / bottom-sheet or drawer nav (mobile), topbar, locale switcher, Clerk <UserButton>, skip link, active-route highlighting
├── content/page.tsx
└── calendar/page.tsx
```

- **Access boundary**: `(dashboard)` routes are already protected-by-default via the existing Clerk middleware posture (ADR-029) — no new auth logic needed, only correct route placement.
- **Incomplete-onboarding redirect**: a Server Component check at the top of `(dashboard)/layout.tsx` calls `GET /accounts/me` (and, if present, checks brand existence via `GET /brands/me`); a signed-in user with no `Account` is redirected to `/[locale]/account-setup`, one with an `Account` but no `Brand` is redirected to `/[locale]/brand-setup` — mirrors [028-m1-technical-design.md](./social-ai-platform/028-m1-technical-design.md) §4.5's documented onboarding flow (account → vertical → brand intake → dashboard), which today has no enforcing code.
- **Navigation**: primary nav is exactly two items — Content, Calendar — plus a disabled/labeled "Settings — coming soon" entry (not a dead link: either non-interactive or routes to an honest placeholder page, never a broken/blank route).
- **No fabricated states**: every list view (`Content`, `Calendar`) fetches from the real endpoints above; empty state shows when the array is genuinely empty (a fresh account), not a fake seeded example. If a demo/example is ever shown, it must be visibly labeled as an example, per the mandate's anti-fabrication rule — no such demo is planned for this pass since real endpoints exist and should be used directly.

## Consequences

**Positive**: every authenticated module maps 1:1 to real, tested backend capability — no honesty risk, no throwaway UI to later rip out. The account-setup gap is closed, which also unblocks a real end-to-end onboarding flow for the first time.

**Trade-offs**: no "AI Workspace" or "Content Library" nav items means the rebuild's visual surface area is smaller than the original prompt's candidate list — flagged here explicitly rather than silently building extra pages to look more complete. Settings being a placeholder is an honest gap, not a defect; it must not be styled to look functional.

**Explicitly deferred**: Stage 2+ features (`ApprovalHistory`, `PerformanceRecord`, analytics, multi-user) remain unbuilt per ADR-018's staged introduction — no page here references them even as "coming soon," since they are not yet product-committed at a level this document should presuppose.
