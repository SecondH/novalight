**Amendment (v1.1, during M1 — SaaS Core Foundation planning):** this ADR originally scoped `Brand`/`ContentIdea`/`ContentDraft`/`CalendarEntry`/`ApprovalHistory`/`PerformanceRecord` only, and referred loosely to an "owning-account" foreign key without ever defining what "account" meant — earlier documents in this set implicitly treated it as synonymous with `User`. M1 planning surfaced that this was ambiguous and needed a real entity. This amendment adds `Account` explicitly (§"Decision" below) as a distinct entity from `User`, before this ADR has been accepted. **Anyone reviewing this ADR for acceptance should treat `Account` as part of what they are approving, not as a pre-existing, already-settled detail.**

**Amendment (v1.2, independent data-architect review of v1.1):** two corrections, both non-structural (no entity added or removed): the ownership-chain cardinality wording was ambiguous (fixed in "Decision" below); and `Account` — unlike its downstream entities — is itself an ownership root with no scoping FK of its own, so its lookup path needed an explicit IDOR rule, now stated in [028-m1-technical-design.md](./028-m1-technical-design.md) §2.2 ("`Account` lookups must never accept a client-supplied `account_id`/`id`").

## Context

[Database Architecture §5](../012-database-architecture.md) and [docs/development/016-phase-0-implementation-status.md](../../development/016-phase-0-implementation-status.md) confirm `packages/database/prisma/schema.prisma` currently contains only the Phase-0-scope `User` model, and that "no other business entities should be implemented before their requirements are approved." This MVP's design ([021-knowledge-model.md](./021-knowledge-model.md)) requires several new entities (Brand Profile, Content Idea, Content Draft, Calendar Entry, and later Approval History, Performance Record) that do not exist today.

This ADR is the "requirements approved" event that constraint anticipates — but approval of direction is not the same as authorization to migrate. See §5.

## Decision

Approve the following entities as the target schema direction for this MVP:

| Entity                  | Purpose                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Introduced at | New in v1.1? |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------- | ------------ |
| `Account`               | Business/tenant ownership container — distinct from `User` (login identity). Every Brand/Content* entity is owned by an `Account`, not directly by a `User`. Stage 1: exactly one `User` per `Account` (the owner-operator, [product/mvp-social-ai/019-personas.md](../../product/mvp-social-ai/019-personas.md) §1). Stage 3+: an `Account` may gain additional `User`s once RBAC is reconciled — this entity exists specifically so that transition doesn't require re-keying every other entity's ownership FK. | Stage 1       | Yes          |
| `Brand` (Brand Profile) | Persistent brand understanding, conceptually defined in [021-knowledge-model.md](./021-knowledge-model.md) §2                                                                                                                                                                                                                                                                                                                                                                                                      | Stage 1       | No           |
| `ContentIdea`           | Planner output                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Stage 1       | No           |
| `ContentDraft`          | Copywriter + Visual Prompt Engineer output, approval state                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Stage 1       | No           |
| `CalendarEntry`         | Scheduled/posted content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Stage 1       | No           |
| `ApprovalHistory`       | Feeds Brand Intelligence Layer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Stage 2       | No           |
| `PerformanceRecord`     | Feeds Analytics Agent                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Stage 4       | No           |

**Ownership chain (notation corrected after independent data-architect review — an earlier version's "1:1 at Stage 1, 1:many from Stage 3" was ambiguous about direction and inconsistent with this same section's own Stage 3 description):** `User` (Phase 0's existing entity, unchanged) —(Stage 1: exactly one `User` owns one `Account`, via `owner_user_id`; Stage 3+: many-to-many — an `Account` may gain additional non-owner `User`s and a `User` may belong to more than one `Account`, via a new join table, additive and non-breaking to `owner_user_id`)→ `Account` —(1:1 at Stage 1 per [product/mvp-social-ai/021-mvp-scope.md](../../product/mvp-social-ai/021-mvp-scope.md) §2's single-brand-per-account rule)→ `Brand` —(1:many)→ `ContentIdea`/`ContentDraft`/`CalendarEntry`/`ApprovalHistory`/`PerformanceRecord`. Every entity from `Brand` downward carries a **direct** `account_id` foreign key to `Account` (not a chain requiring a join through `Brand` — see Consequences below, unchanged from the prior version of this ADR).

All entities follow existing [Database Architecture](../012-database-architecture.md) conventions unchanged: PostgreSQL via Prisma only, `snake_case` naming, UUID primary keys, `created_at`/`updated_at`, migrations required, no direct production schema modification. `Account` itself has no owning FK (it is the ownership root) but does carry a `user_id` (or, once Stage 3 arrives, a join table) FK back to the `User`(s) that may act on it.

## Reasoning

- Every Brand/Content* entity traces directly to a specific agent input/output already specified in [020-ai-agent-specifications.md](./020-ai-agent-specifications.md) — none is speculative or added "just in case," consistent with [ADR-014](../006-initial-architecture-decisions.md).
- `Account` is the one entity in this ADR that doesn't trace to an agent I/O — it traces instead to the M1 planning requirement to model "business ownership" as distinct from "user accounts" ([docs/development/018-mvp-m1-plan.md](../../development/018-mvp-m1-plan.md)) and to the ownership-scoping requirement independent reviewers already required (§"Consequences" below). Introducing it now, while Stage 1 is still single-user, is not premature: modeling ownership correctly from the first migration avoids a breaking schema change when Stage 3 introduces multiple `User`s per `Account` — the alternative (treating `User` as the owning entity directly, then migrating every Brand/Content* table's FK later) is a larger, riskier change deferred to exactly when RBAC work is already underway.
- Staging entity introduction by MVP Track stage (Stage 1 vs. Stage 2 vs. Stage 4) avoids creating `ApprovalHistory`/`PerformanceRecord` tables before any feature reads or writes them.

## Consequences

Positive:

- Implementation work (per [product/mvp-social-ai/027-development-plan.md](../../product/mvp-social-ai/027-development-plan.md) M1) has an approved, traceable target instead of ad hoc schema design at build time.

Trade-offs / open items:

- **Every** entity in this ADR below `Account` — `Brand`, `ContentIdea`, `ContentDraft`, `CalendarEntry` at Stage 1, and `ApprovalHistory` (Stage 2) and `PerformanceRecord` (Stage 4) when their stages are reached — requires a direct `account_id` foreign key to `Account` from its own first migration, independent of RBAC. This is basic resource-ownership scoping, not multi-tenant/RBAC design, and is not blocked by the open RBAC decision (see [018-saas-architecture.md](./018-saas-architecture.md) §4, amended after independent security review to make this explicit). An earlier version of this ADR stated this requirement for the Stage-1 four only; extended here after independent data-architecture review found the omission — `ApprovalHistory` and `PerformanceRecord` must not rely on transitive ownership inferred through a join (e.g. `ApprovalHistory → ContentDraft → ContentIdea → Brand`), which would be both a query-complexity and an enforcement-gap risk. What genuinely _is_ deferred to Stage 3 pending RBAC reconciliation is any column/relation representing roles, teams, or multi-user permission scope on top of these ownership FKs — not the FKs themselves.
- **Enforcement point, corrected after independent review:** ownership scoping is enforced at the Repository layer (`WHERE account_id = :requestingAccountId` on every query touching these entities), not by `packages/auth`'s `AuthorizationProvider` interface alone — that interface checks resource-type/action permissions, not row-level ownership. See [018-saas-architecture.md](./018-saas-architecture.md) §4 for the corrected mechanism.
- No entity in this list stores social-platform credentials or tokens — that would only arise with [026-future-social-api-integration.md](./026-future-social-api-integration.md), explicitly out of scope.

## §5 — What This ADR Does Not Do

**This ADR approves direction, not implementation.** Consistent with the user's explicit instruction for this documentation pass ("do not implement until documentation is approved," "do not write application code yet"):

- No migration is created or run as part of this ADR.
- `packages/database/prisma/schema.prisma` is unmodified by this documentation pass.
- Actual schema authorship (column types, indices, relations) happens at implementation time, under [database-change-review](../../../.claude/skills) / the `data-architect` agent, per [CLAUDE.md §12](../../../CLAUDE.md#12-subagent-routing).
- This ADR itself requires human acceptance (per its Proposed status) before it can be cited as the "approved requirements" [Database Architecture §5](../012-database-architecture.md) requires.
