# Workspace Maintenance Runbook

How to extend, audit, and safely test the `.claude/` workspace.

## Add a new skill

1. Create `.claude/skills/<name>/SKILL.md` with frontmatter `name` and a `description` specific enough to self-select correctly (state both when to use it and, if likely to be confused with another skill, when not to).
2. Follow the structure used by existing skills: Purpose, Use When, Required Inputs, Preconditions, Workflow, Validation Checklist, Outputs, Escalation Conditions, Prohibited Actions.
3. Add a row to the routing table in [CLAUDE.md §13](../../CLAUDE.md#13-skill-routing).
4. Check for overlap with an existing skill — if two skills would both claim a task, narrow one or merge them.

## Add a new agent

1. Create `.claude/agents/<name>.md` with frontmatter `name`, `description` (when to use it), and `tools` (explicit allow-list — review agents should generally omit `Edit`/`Write`).
2. Follow the structure: Mission, Scope, Inputs, Required Context, Analysis Method, Output Contract, Severity Model, Escalation Rules, Boundaries, Prohibited Actions.
3. Add a row to the routing table in [CLAUDE.md §12](../../CLAUDE.md#12-subagent-routing) and to the ownership table in [agent-governance.md](./agent-governance.md).
4. If the agent reviews changes, confirm it isn't the sole reviewer of anything it (or a closely related agent) also implements — see reviewer independence in [agent-governance.md](./agent-governance.md).

## Add a new command

1. Create `.claude/commands/<name>.md` with a `description` frontmatter field.
2. Keep it a thin wrapper: sequence existing skills/agents; don't duplicate their workflow logic inline.
3. Add a row to the catalogue in [CLAUDE.md §14](../../CLAUDE.md#14-command-catalogue).

## Add a new hook

Hooks are the highest-risk workspace component — a bad hook can silently fail open (worse than no hook) or block legitimate work with false positives. Follow this procedure:

1. Write the hook script in `.claude/hooks/<name>.js` (Node.js — cross-platform, no shell dependency for anything beyond reading stdin JSON).
2. Read tool-call JSON from stdin (`tool_input`, `cwd`, etc.); communicate via exit code only: `0` = allow, `2` = block (stderr = reason shown to the user/model). Advisory-only hooks should always exit `0` and use stderr purely as a message.
3. **Avoid subprocess calls where a pure filesystem/string check will do.** During this workspace's bootstrap, `protect-main-branch.js` originally used `child_process.execSync`/`execFileSync` to run `git branch --show-current` — this proved unreliable on Windows (intermittent `ENOENT` spawning `git`/`cmd.exe` depending on the invoking shell), causing the hook to silently fail open. It was rewritten to read `.git/HEAD` directly, which is deterministic and has no PATH/shell dependency. Prefer this pattern for any future hook that needs git state.
4. **If a hook does need a `cwd` argument from the hook input JSON, do not assume it's in the host's native path format.** In this environment (Windows + Git Bash), a POSIX-style path (`/c/Users/...`) fed through `path.resolve()` on win32 Node is silently mis-resolved against the _current drive_ rather than erroring — a silent-wrong-answer failure mode, not a crash. `protect-main-branch.js` normalizes `/x/...` paths to `X:\...` defensively before use; replicate this if a new hook resolves paths from `cwd`.
5. **Test with harmless positive and negative cases before wiring into `settings.json`** — pipe synthetic JSON directly into the script:
   ```
   echo '{"tool_input":{"command":"<test command>"}}' | node .claude/hooks/<name>.js; echo "exit:$?"
   ```
   For hooks needing `cwd`/git state, build a throwaway git repo in the scratch directory, exercise both branches of the condition, and delete it afterward — never test against a real repository's actual `main` branch.
6. Wire into `settings.json` under the correct event (`PreToolUse` for blocking, `PostToolUse` for reminders) and matcher (tool name, `|`-separated for multiple).
7. Validate JSON syntax: `node -e "JSON.parse(require('fs').readFileSync('.claude/settings.json','utf8'))"`.
8. **Known limitation**: hooks added to `settings.json` after a session starts are not always hot-loaded — the settings watcher only watches directories that had a settings file at session start. If a newly-added hook doesn't seem to fire, tell the user to run `/hooks` once or restart. (In practice, during this workspace's own bootstrap, the hooks fired live within the same session that created `settings.json` — see the note below.)

## Remove obsolete instructions

Before deleting a skill/agent/command/hook: grep `CLAUDE.md`, `docs/ai-workspace/*`, and other `.claude/` components for references to its name. Remove the references first, then the file, in the same change — a dangling reference is a documentation-integrity bug (see `documentation-maintenance` skill).

## Resolve conflicting instructions

Same rule as project documentation conflicts ([CLAUDE.md §3](../../CLAUDE.md#3-authoritative-documentation)): report the conflict to the user; do not silently pick a winner. See [agent-governance.md](./agent-governance.md) "Conflict resolution."

## Audit workspace quality

Use `/workspace-audit`. It scores against the maturity model below, **only where evidence supports a score** — an unscored category should say so, not receive an invented number.

### Maturity model (score 0–10 per category, evidence required)

instruction clarity · documentation coverage · skill quality · agent specialization · command usefulness · hook effectiveness · security controls · testing integration · architectural alignment · redundancy (lower duplication = higher score) · stale content (less staleness = higher score) · false-positive hooks (fewer = higher score) · missing escalation rules · context efficiency

No scores are assigned at bootstrap time — there is no usage history yet to evidence them. Run `/workspace-audit` after the workspace has seen real use.

## Update documentation routing

When a new `docs/` document is added, update the routing table in [CLAUDE.md §3](../../CLAUDE.md#3-authoritative-documentation) in the same change.

## Validate links

Run `/verify-links` (backed by `documentation-maintenance`). It checks every relative link in `docs/**/*.md` and `CLAUDE.md` resolves, and separately reports already-known dead references (`docs/decisions/`, `docs/api/`, `docs/engineering/technical-debt.md`, `docs/engineering/engineering-constitution.md`) versus newly discovered ones.
