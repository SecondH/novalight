## 0. Why `docs/deployment/` and `docs/operations/` Are New Top-Level Categories

Flagged explicitly, per the same principle applied to the earlier `docs/testing/` question (that time, folded into `docs/development/` instead — see `.claude/memory/known-risks.md` history). This time the call goes the other way, for a stated reason: production/deployment/operations concerns (CI/CD mechanics, environment topology, secrets, monitoring, staging architecture) have **no existing home** in the current tree — unlike testing, which Engineering Constitution §7 and Development Workflow §12 already substantially covered. `docs/architecture/006-initial-architecture-decisions.md`'s ADR-012 only names _where_ things deploy (Vercel/Railway/Supabase), not _how_ (environments, secrets, CI/CD, monitoring). This is also plausibly a growing domain (staging runbooks, incident response, disaster recovery) rather than a single document, unlike the testing case. Both categories follow the standard flat `NNN` convention like every other substantive category (not the unnumbered `ai-workspace/`/`readiness/` pattern, since these are real, evolving project documentation, not meta-workspace or point-in-time-assessment artifacts).

## 2. Architecture Recommendation

No change to ADR-012's targets (Vercel/frontend, Railway/backend, Supabase/database) — no new evidence from M1 suggests reconsidering them, and re-litigating an accepted ADR without cause would itself violate ADR-014. This plan operationalizes ADR-012, it doesn't replace it.

```text
                    ┌─────────────┐
   Developer  ──▶   │   GitHub    │  (assumed host -- no remote configured in this
                    │  (proposed) │   repository yet; confirm before treating as settled)
                    └──────┬──────┘
                           │ CI/CD (platform: open decision, §6)
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │  Vercel  │ │ Railway  │ │ Supabase │
        │  (web)   │ │  (api)   │ │   (db)   │
        └──────────┘ └──────────┘ └──────────┘
         staging + production, each with its OWN project/service/instance
         per docs/operations/023-environment-strategy.md §1 and §6
```

Each of the three platforms already natively supports the staging/production separation [023-environment-strategy.md](../operations/023-environment-strategy.md) requires (Vercel: separate projects or environments; Railway: separate services; Supabase: separate projects) — no additional infrastructure layer (e.g. Kubernetes, a custom orchestration platform) is justified by anything M1 needs, consistent with ADR-014.

## 3. Database Migration Strategy

- **Tool: unchanged** — Prisma, per ADR-006. `prisma migrate deploy` (non-interactive) runs in the CI/CD pipeline against each environment's `DATABASE_URL`; `prisma migrate dev` remains local-developer-only (already the case, unchanged).
- **Sequencing:** migration deploy step runs _before_ the application deploy step in any pipeline, so the running application code never queries a schema it doesn't expect. Standard, not novel.
- **Rollback:** Prisma migrations are forward-only by default; a rollback strategy (revert migration vs. roll-forward fix) is **not decided here** — flagged as a production-readiness gate item (§8), not invented speculatively.
- **Backup/recovery:** still an open, pre-existing tracked risk (`.claude/memory/known-risks.md` "No recovery/backup strategy documented") — this plan does not close it, see [023-environment-strategy.md](../operations/023-environment-strategy.md) §6 for the same flag.

## 4. Secrets Management Strategy

See [023-environment-strategy.md](../operations/023-environment-strategy.md) §3 for full detail — summary: hosting-platform-native environment variables (Vercel/Railway/Supabase project settings) plus CI/CD-platform-native secrets store, no dedicated secrets-management product introduced (unjustified complexity per ADR-014).

## 5. Monitoring and Logging Strategy

## 7. Implementation Sequence (For When Decisions Are Made — Not Started)

1. Human decision on CI/CD platform (#3) — blocks everything downstream that touches automated deployment.
2. Provision staging: Supabase staging project, Railway staging service, Vercel staging project/environment, Clerk staging instance.
3. Wire environment variables per [023-environment-strategy.md](../operations/023-environment-strategy.md) §2-3 into each staging service.
4. Add a deploy step to CI/CD: migration deploy → backend deploy → frontend deploy, staging only, on merge to `main`.
5. Implement `apps/api/src/auth/clerk-auth-provider.ts` (real Clerk integration) per [022-authentication-production-strategy.md](../security/022-authentication-production-strategy.md) §2 — the one piece of _code_ this planning round identifies as needed, explicitly deferred to a future implementation session, not written now.
6. Validate staging end-to-end (M1's actual user journeys, against real Clerk + real Supabase, still with the fake AI provider — no M2/real-vendor AI work here).
7. Only then: formalize production deploy trigger and gate (#4, #5), provision production instances mirroring staging.

No M2 product features appear anywhere in this sequence, per explicit instruction.
